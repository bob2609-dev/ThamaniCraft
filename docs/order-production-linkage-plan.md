## Goal and baseline

Connect customer orders to recipe-based work orders, safe production completion, delivery/collection and actual profitability. Customer intake, inline customer creation, upfront fixed discounts, payments, recipe mapping and production planning exist; work-order linkage and stock posting do not. Authenticated browser acceptance remains pending.

This is the coordinating sequence for the [Customer Orders plan](customer-orders-implementation-plan.md) and [Production plan](production-implementation-plan.md); their detailed rules still apply. No application or database changes are part of this planning task.

Customer order → confirmed recipe-backed lines → linked work orders → inventory-confirmed good output → ready → delivered/collected. Payments are tracked independently throughout.

## Implementation sequence

Complete each stage's checks before marking it done. Add its API and UI together, retaining Inventory/Procurement colours and back-to-list navigation.

1. [ ] **Order lifecycle — Sales service, OrderEntry and Sales pages.** Add readable order numbers, optimistic versions, edit/confirm/pre-production cancel actions and audit history. Add status, due-date, overdue and payment filters as their data becomes available. Preserve customer snapshots and audit discount changes. Verify stale edits fail, cancelled orders retain history and only confirmed orders can generate production.
2. [ ] **Payments and balances — Sales and Identity.** Add append-only payment receipts (amount/date/method/reference), idempotent recording, separately authorised reasoned reversals, net paid, deposit shortfall and outstanding balance. Use transactional locking to reject concurrent overpayments; reject order-total reductions below net paid. Distinguish correction of an erroneous receipt from an actual refund: cancellation retains receipts and shows refund due; real refund recording is deferred, not simulated by reversal. Verify the 95,000 total / 30,000 payment / 65,000 balance example and duplicate/concurrent submissions.
3. [ ] **Recipe/output mapping — Sales, Production and Inventory.** Map each producible order line to a recipe and finished product with compatible output UOM; explicitly convert ordered quantity to planned recipe output. Save standard-cost snapshots separately from selling prices. Custom descriptions remain valid intake but cannot generate work until mapped. Verify recipe scaling, pieces versus trays and rejection of incompatible units.
4. [ ] **Durable order/work-order linkage — Sales and Production.** Add Create work order on confirmed order lines, order/line references on batches and reciprocal links/statuses in both detail pages. Validate tenant, permissions and order version server-side; persist generation intent and retry safely across service failures. Enforce a unique generation key so retries cannot duplicate batches. Initially generate one batch per line; explicit shortfall/replacement batches require a new audited request. Freeze production-affecting line edits while linked work exists; cancellation must resolve unstarted batches. After production starts, use a dedicated cancellation/settlement workflow retaining consumption, costs and output history; the direct cancel action remains blocked until that workflow exists. Verify concurrent edit/generation/cancel, duplicate retries and cross-tenant requests.
5. [ ] **Actual production and reliable posting — Production, Inventory and RabbitMQ.** Record actual consumption, good output, scrap, confirmed labour/energy/manual overhead and batch extras. Add immutable inventory movements, stable-order material locks and atomic shortage checks/deductions/output credit. Use transactional outbox, deduplication and durable result delivery; show completion pending/failed and retry controls, never Completed before inventory success. Version corrected attempts after a rejected posting; replay successful results without reposting. Verify shortages cause no partial writes, broker/crash recovery, duplicate messages and zero-good-output loss costing.
6. [ ] **Readiness and fulfilment — Sales and Inventory.** Allocate inventory-confirmed output to its order lines, preventing the same output serving two orders. Require enough good output for every line before Ready; scrap/shortfall stays visible and allows explicit follow-up production. Record collection/delivery date, actor and reference, with idempotent finished-stock dispatch; mark fulfilled only after posting success. No partial deliveries initially. Verify shortfalls, concurrent allocation, repeated dispatch and standalone stock-production batches.
7. [ ] **Order actual costs and margin — Sales detail.** Attribute actual costs from allocated batch output, plus manually entered order extras such as delivery expense. Keep customer delivery charge as revenue, not expense; prevent duplicate allocations and double-counted overhead. Label incomplete actual costs, planned margin and final actual margin distinctly; later recipe/material price changes must not rewrite snapshots. Verify shared-output allocation totals and discounted revenue minus attributable costs.
8. [ ] **Final verification and development release.** Run Sales/Production/Inventory security, unit, integration and concurrency tests; frontend build/lint; authenticated customer-create → discounted order → payment → production → fulfilment browser checks. Rehearse forward migrations on copied data, back up before deployment, verify service/broker health and reload Nginx after gateway/UI recreation. Update PROGRESS with exact evidence and remaining gaps; HTTP 200 alone is not browser acceptance.

## Boundaries and completion criteria

- Dependencies: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. Start with order lifecycle, then payments; do not enable fulfilment before safe posting exists.
- Services own their data: Sales owns commercial/payment records, Production owns execution, Inventory owns stock/value movements. Use authenticated tenant-scoped contracts, not direct cross-service table writes. Determine forward migration numbers from current Flyway history; never rewrite applied migrations or clear development records.
- No automatic depreciation, forecasts, Finance expense allocation, accounting journals or payment-provider integration. Recipe labour/energy/overhead and order extras remain explicitly entered. No automatic stock reservation at start; recheck atomically at completion. Finished-output allocation is separate from raw-material reservation.
- Approved policy (2026-09-24): mapping and preparation may happen before any/full payment; unpaid/deposit warnings do not block confirmation, preparation or fulfilment. Payment and fulfilment statuses remain separate. Cancellation after preparation must be recordable through the dedicated workflow described in [the focused plan](payment-independent-production-plan.md). UI must disclose deferred refunds, returns, partial deliveries and completed-batch reversals.
- Done when one customer order can be traced through linked production, stock movements, payment history, fulfilment and cost breakdown without duplicate payments, batches or stock postings, with tenant isolation and authenticated acceptance evidence recorded.
